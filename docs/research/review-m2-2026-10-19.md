# M2 review: the MLX backend and its neighbours

Reviewer: an independent agent, reading code only (no JVM, test or build was
run). Reviewed at HEAD `16faf89` ("Linux bring-up on the Jetson Thor..."),
which landed during the review. It changed only `src/gen/backend/mlx.clj`
(the CPU-compile probe, lines 1167-1204 and 1215) among the files under
review, so line numbers after 1166 in that file refer to the new version.

Where a finding depends on MLX's or the JDK's behaviour, I checked the MLX
0.32.2 / mlx-c 0.7.0 sources in `native/build/src/` and say so. Each finding
says whether it is **confirmed** (follows from the code as written) or a
**suspicion** (plausible, but it needs a test to confirm).

Severity order: correctness first, then native memory and lifetime, then
errors that are not loud, then docs.

## 1. `array/compile` binds inputs by the first call's map order (HIGH, confirmed)

`src/gen/array.clj`:

```clojure
621:  (cond (map? t) (mapcat tree-leaves (vals t))
...
1009:             leaves (vec (tree-leaves args))]
1020:             (let [skel (skeleton args)
1021:                   entry (or (get @compiled [b skel])
1024:                                                     (let [out (apply f (refill skel ins))]
1031:                   ins (with-backend b (mapv #(if (host? %) (array % {:dtype (weak-dtype % b)}) %) leaves))]
```

The cache is keyed by the skeleton, compared with `=`, so `{:a nil :b nil}`
and `{:b nil :a nil}` are the same key. But the leaves are listed in the
current call's map iteration order (`vals`), and the cached `g` rebuilds the
arguments from the **first** call's skeleton (`skel`, captured by the closure
at 1024). Two equal maps with different iteration orders therefore bind
values to the wrong keys. MLX's cache checks only the shapes and dtypes of
each input position, so when the swapped leaves share a shape and dtype
nothing retraces and nothing complains.

Scenario (MLX, any device):

```clojure
(def cf (array/compile (fn [{:keys [mu sd]}] (/ mu sd))))
(cf {:mu 1.0 :sd 4.0})   ; 0.25: traced with leaves [mu sd]
(cf {:sd 4.0 :mu 1.0})   ; leaves [4.0 1.0], refilled into {:mu _ :sd _}: 4.0
```

On the JVM backend `compile` is `(apply f args)` and both calls give 0.25,
so this is also a difference between backends. Since 16faf89 the same thing
happens on MLX's CPU device where `compiles?` is false: `-compile` returns
`f`, the gen.array wrapper, which still refills from the first skeleton
(mlx.clj:1215).

Array maps keep insertion order, so the trigger is ordinary user code
(literal maps, `assoc` in different orders, `zipmap`). Inside the library,
`mcmc`'s compiled steps are not affected in practice: `others` comes from
`sel/get-selected`, which rebuilds in canonical sorted order
(selection.clj:93-99), so equal structures enumerate alike.

**Test.** In `compiled-functions` (test/gen/array_test.clj:238), call `cf`
with `{:mu 0.5 :sd 2.0}` and then `{:sd 2.0 :mu 0.5}` and compare both with
`f`. The current test always uses one literal order, so it cannot fail.

**Fix direction.** Get the leaf order from the cached skeleton (walk `skel`'s
keys and look each one up in `args`), or key the cache by an
order-sensitive form (keys in iteration order).

## 2. Scratch arguments over 1 KB leak native memory for the thread's lifetime (MEDIUM-HIGH, confirmed)

`src-java/gen/mlx/MlxRuntime.java`:

```java
121:    private final Arena arena = Arena.ofAuto();
...
144:    private MemorySegment bump(long bytes) {
145:      long aligned = (bytes + 7) & ~7L;
146:      if (pos + aligned > buf.byteSize()) {
147:        if (aligned > buf.byteSize() / 2) return arena.allocate(aligned, 8);
148:        buf = arena.allocate(buf.byteSize() * 2, 8);
```

`scratch()` resets `pos` to 0, so any one argument block larger than `buf`
(1024 bytes, which never grows for large requests) takes the line 147 path:
a fresh allocation from the thread's automatic arena. An `Arena.ofAuto()`
frees its memory only when the arena and all its segments are unreachable.
The arena belongs to the thread's `Scratch`, held by a `ThreadLocal` (line
191), so every such allocation lives as long as the thread: the main thread's
for the whole run.

Callers that exceed 1 KB, meaning more than 128 handles in one
`vectorOf` (line 409):
- `eval-arrays!` (mlx.clj:411-412). `gfi/eval-trace!` runs once per
  inference iteration over every choice, the retval and the score.
- `concatenate` (mlx.clj:645-647). `cm/to-array` concatenates every
  selected latent, once or twice per HMC or MALA step.
- the compiled-call input vector (mlx.clj:1156). A compiled HMC step passes
  every leaf of `others`.

Scenario: MH or HMC on a model with 300 scalar sites. Each `eval-trace!`
leaks at least 2.4 KB, and a compiled step about as much again; 10^6
iterations leak several GB of native memory. That matters on this machine,
whose memory guards exist because of an earlier kernel panic.

**Test.** A unit test on the binding:
`(= (.address (.longs (MlxRuntime/scratch) (long-array 200))) (.address (.longs (MlxRuntime/scratch) (long-array 200))))`.
It is false today (a new address every call). Or a bounded loop of
`array/eval!` over 200 arrays, checking that native memory (NMT `Other`)
stays flat.

**Fix direction.** Grow `buf` to fit the request and keep it, rather than
making a one-off allocation.

## 3. A compiled function called from a second thread leaves a stale MLX compile-cache entry (MEDIUM: the leak is confirmed, wrong results are a suspicion)

MLX's compile cache is thread-local, and an entry is erased only from the
cache of the thread that called `mlx_compile`:

- `native/build/src/mlx/mlx/compile.cpp:415`: `static thread_local auto cache = ...`
- `:1145`: a call looks up `compile_cache_unsafe()->find(fun_id, ...)`, the
  **caller's** thread cache, and fills a new entry there on a miss.
- `:1248-1253`: the deleter captures `cache = detail::compile_cache()` at
  compile time, the **creator's** cache:
  `detail::compile_erase(cache, reinterpret_cast<std::uintptr_t>(p)); delete p;`

gen.clj makes one MLX compiled closure per `[b skel]` on whichever thread
calls first (array.clj:1021-1029, mlx.clj:1152), then applies it from any
thread (mlx.clj:1158). `mcmc/compiled-steps` is global (mcmc.clj:66-69), and
the docs say arrays move freely between threads, futures included. The
closure is freed by whichever thread drains (`adoptClosure`,
MlxRuntime.java:277-310).

What follows:
- **Leak (confirmed).** Thread A compiles, thread B calls. When the
  function is freed, only A's entry is erased. B's entry stays until B
  exits, with its traced tape and every constant the trace captured (for
  example a model's closed-over data). With pooled threads, that is the
  life of the process.
- **Wrong results (suspicion).** B's stale entry is keyed by the address of
  a deleted `std::function`. A later `mlx_compile` that gets the same
  address from malloc, called on B with the same input shapes and dtypes and
  the same default stream, hits the stale entry (`entry.empty` is false) and
  replays the old tape. MLX never calls the new function's `run`, so
  gen.array's `out-skel` stays nil, and `(refill nil outs)` (array.clj:1034)
  returns the first output: a single-output compiled function silently
  returns the old function's value. Whether this happens depends on
  allocator address reuse, so it needs a test to confirm.

For `mcmc` specifically, a replayed wrong leapfrog does not bias HMC: the
acceptance uses the plain kernel's scores, and any leapfrog map is
volume-preserving and reversible. The exposure is direct `array/compile`
users.

**Test.**
- Leak: compile a function that closes over a large MLX constant, call it
  on a `future` and then on the main thread, drop it, run `mlx/collect!`,
  and check that `(:active (mlx/memory))` returns to its baseline. It will
  not.
- Wrong results: on one thread, many rounds of
  `(array/compile (fn [x] (* x i)))` called with the same shape, after
  rounds that made each function on a future and called it on this thread.
  Assert every result is `i·x`.

**Fix direction.** Make compiled closures per thread: include the thread in
gen.array's cache key, so each thread calls `mlx_compile` itself and the
deleter targets its own cache.

## 4. Reference spot checks on lazy backends flag float32 rounding as divergence (MEDIUM, suspicion with worked numbers)

`src/gen/batched.clj`:

```clojure
202:  (case (array/dtype x) (:float16 :bfloat16) 1e-2 :float32 1e-5 1e-8))
214:              (<= (Math/abs (- u v)) (* rtol (max 1.0 (Math/abs u) (Math/abs v))))))
276:        rtol (max (tolerance-of (:score t)) 1e-8)
289:            (when-not (and (close-host-values? (array/->clj (:score st)) (particle-host score i) rtol)
```

Since genclj-w5y0, a batched MLX trace is checked against a float64 JVM
re-run. The tolerance is 1e-5 times |score|. Float32 error grows instead
with the conditioning of each site: residuals of large observations divided
by a small sd.

Worked example: a regression with x = 1000..1999 (host args), y ≈ 2x + 1
observed as host doubles, sd 0.01, a per-particle latent intercept near 1.
In the batched run, `mu` (about 4000) and `y` are rounded to float32 (ulp
about 2.4e-4, half-ulp about 1.2e-4), so z = (y − mu)/0.01 is off by about
0.02 per site, and each log-prob term by about z·0.02. Summed over 1000
sites with random signs, that is about 0.6 nats. The score is about
1000·(4.6 − 0.92 − 0.5) ≈ 3190, so the tolerance is 0.032. The check reports
a mismatch. With sd 0.1 the numbers are about 0.1 against 0.009.

Consequences:
- After a batched simulate or generate: a silent fallback to per-particle
  MLX runs (a large slowdown), with a misleading `fallback-reason` ("the
  code branches on a batched value...").
- After unchecked updates (a particle filter): a loud `::diverged` error on
  a correct model.

`spot-check-here!` (MLX against MLX) would have passed, since both runs make
the same float32 roundings.

**Test.** The model above, batched `generate` on MLX float32 with 64
particles: assert `(batched/fallback-reason ps)` is nil. A particle-filter
variant: assert there is no `::diverged`.

**Fix direction.** Treat the reference run as a filter: confirm any
mismatch with `spot-check-here!` for that particle before falling back or
diverging. Or scale the tolerance with the sites' magnitudes rather than the
total.

## 5. Native mode inside compile differentiates the exact composites into NaN (MEDIUM-LOW, confirmed by reasoning; opt-in configuration)

```clojure
mlx.clj:901   (defn- custom-vjps? [] (and (= grad-mode :native) (not *tracing-compile*)))
mlx.clj:939   (if-not (custom-vjps?)
mlx.clj:940     (route op xs)
exact.clj:21  (array/where (< x 0.0)
exact.clj:22               (/ 1.0 (+ (array/expm1 (array/negate x)) 1.0))
```

With `-Dgen.mlx.grad=native` inside `array/compile`, MLX differentiates the
composite's graph. For float64 x < −709.78 the **chosen** branch has
`expm1(−x) = inf`. Its VJP takes `−g/(inf)² = −0` into expm1's VJP, which
multiplies by `exp(800) = inf`: `0·inf = NaN`. The true derivative,
`exp(x)`, is 0. The exact `exp` sits under:
- `logsumexp` (`exp(x − m)`), used by the mixture log-probs at dist.clj:431
  and :459;
- the float64 `logaddexp` route (exact.clj:126), used by `beta-uniform` at
  dist.clj:145;
- `softplus` and `sigmoid`.

So float64 (CPU, dtypes 64) compiled gradients are NaN once two log terms
differ by more than about 710, which is common in mixtures. On Metal, the
float32 Kahan `expm1` route has the same flaw for x below about −87: when
`u = 0`, `safe` stays 0 (exact.clj:115), and `log`'s VJP gives `0/0`. Core
code does not call `expm1`, so this reaches only user models.

Tape mode and native mode outside compile are fine: there the op is a
primitive with the rule `g·out`.

In `mcmc`, this surfaces loudly ("The acceptance ratio is NaN"). Direct
compile+grad users get silent NaN.

**Test.** Native mode, a `{:device :cpu :dtypes 64}` backend:
`((array/compile (array/grad #(array/sum (array/logaddexp % -800.0)))) (array/array [0.0]))`
should be `[1.0]` (the tape gives that) and is `[NaN]`.

**Fix direction.** Give the value by the exact route and the gradient by
MLX's own op: `(+ approx (stop-gradient (- exact approx)))`. Or add stand-ins
for the overflow lanes.

## 6. Collections livelock above `MAX_ARRAYS` (MEDIUM-LOW, confirmed; a performance cliff, not an error)

```java
272:    if (live > arrayThreshold || fresh > NEW_BYTES || ...) collect();
315:    if (LIVE.get() <= arrayThreshold && FRESH.get() <= NEW_BYTES && activeMemory() <= byteThreshold) return;
330:    arrayThreshold = Math.min(MAX_ARRAYS, Math.max(BASE_ARRAYS, 2 * LIVE.get()));
```

Once more arrays are genuinely live than `MAX_ARRAYS`, the threshold is
reset to `MAX_ARRAYS`, below the live count, after every collection. From
then on, every `wrap`, so every op result, calls `collect()`: a full
`System.gc()` plus at least one 10 ms `OWNED_QUEUE.remove(10)` timeout.
`MAX_ARRAYS` is about 299,000 on Metal (60% of `resource_limit`) and 300,000
everywhere else, including Linux CPU, where there is no buffer limit at
all.

Scenario: about 10,000 scalar traces of a 30-array model kept alive (the
working set docs/array-api.md §13 describes). After that, each op costs at
least 10 ms, which looks like a hang rather than an error.

**Test.** Hold 310,000 arrays, run 100 ops, and assert that `:collections`
grows by only a handful (or that the ops take well under a second).

**Fix direction.** Back off: after a collection that freed little, set the
threshold above the live count, or rate-limit collections. Warn near the
real limit.

## 7. `:compile? true` does not fall back as documented (LOW, confirmed)

The doc (array-api.md §8, and `hmc`'s docstring) says a model that cannot be
compiled "falls back to the plain kernel". The code falls back only on
ex-info with `:op :compile` (mcmc.clj:84-88; mlx.clj:1143-1149). And
`array/compile` turns host leaves into backend arrays (array.clj:1031).

- An observed host value used as a host number, for example
  `(dotimes [i (trace :n (poisson 4))] (trace [:x i] (normal 0 1)))` with
  `:n` observed as `4`, becomes an MLX int32 array inside the compiled
  trace. `dotimes` then does `(long n)`, which throws `ClassCastException`.
  That is not ex-info, so it escapes compiled-step and HMC throws, while the
  plain kernel (where `n` is a host Long) works.
- A non-array choice value (from a user distribution) throws at
  `structure`/`array/shape` (`{:op :shape}`, mcmc.clj:77), or at the leaf
  check (array.clj:1011-1016, which has no `:op`). Again the plain kernel
  would work.
- Related: on MLX, `((array/compile (fn [x] (* x 0.1))) 3.0)` gives a
  float32 MLX array (0.3) where the uncompiled function gives the host value
  0.30000000000000004 (and the JVM backend's compile is the identity). This
  is the same kind of discrepancy 4697cfd just removed from the tape.

**Test.** The `dotimes` model: `hmc` with `{:compile? true}` should not
throw, and should give the same acceptance pattern as without compile for a
fixed key.

## 8. Native-mode linear-algebra VJPs make arrays on `*backend*`, not the op's backend (LOW, confirmed; opt-in mode)

```clojure
tape.clj:106  (let [n (peek (array/shape x)) i (array/reshape (array/arange n) [-1 1]) ...
tape.clj:206  eye (array/eye n)
tape.clj:241  inv (p/-linalg inner :solve [m (array/broadcast-to (array/eye n) (array/shape m))])
```

The tape binds `array/*backend*` to `inner` around its backward pass
(tape.clj:455). The MLX custom VJP callback (mlx.clj:952-956) does not. So in
native mode, `cholesky` and `slogdet` gradients make `eye` and `arange` on
whatever `*backend*` is: the JVM by default, or another MLX instance. Mixing
them fails with "arrays from different backends".

Scenario: native mode, no `-Dgen.backend=mlx`, an MLX matrix `a`, and
`((array/grad #(array/sum (la/cholesky %))) a)`. The tape gives a gradient;
native mode throws.

**Test.** Exactly that, also with two MLX instances (CPU and GPU).

**Fix direction.** `(array/with-backend b ...)` around the rule in `linalg`'s
custom VJP, or `with-backend inner` inside `linalg-vjp`.

## 9. Tracked values with host primals are strongly typed (LOW, confirmed)

```clojure
tape.clj:45   (dt/with-weak nil #{(dt/kind (dt/host-dtype v))} (p/-defaults inner))
array.clj:251 (and (backend-array? x) (backend-array? y))
array.clj:253 (if (identical? dx dy) dx (dt/promote dx dy)))
```

A `Tracked` whose primal is a host Double reports the backend's default
float and counts as a strong array in `ew2`. Untaped, the same host number
is weak.

Scenario (JVM backend):
- `xs = (array/array [1.5 2.5] {:dtype :float32})` and
  `f = (fn [s] (array/sum (* s xs)))`.
- `(f 2.0)` is float32.
- The value from `((array/value-and-grad f) 2.0)` is float64.

On MLX in 32-bit mode the same happens with float16 data (float32 taped,
float16 untaped). Taped and untaped results therefore differ in dtype, and
so in rounding.

A related note: gradients of functions of host scalars on MLX are float32
MLX arrays, because the seed `ones-like` is made on `inner`
(tape.clj:426). The values stay float64 on the host, as §8 now says, but the
gradients do not.

**Test.** A property: for f over host scalars and arrays of other float
dtypes, the value from `value-and-grad` equals `(f x)` in dtype and value.

## 10. Missing reachability fences (LOW, suspicion: narrow race windows)

- mlx.clj:320-321 (`from-values` for float16/bfloat16):
  `(wrap b (Mlx/mlx_astype (.-h ^MlxArray x) ...))`. Nothing keeps `x`
  reachable during the downcall.
- mlx.clj:909, :1150 and :1106-1107:
  `(MlxRuntime/retain (.-h ^MlxArray (as-array b % nil)))`. For a host
  result, `as-array` makes a new array that is unreachable as soon as `.-h`
  is read.

If a GC enqueues the phantom during the downcall and another thread drains,
`mlx_array_free` runs while this thread passes the handle: a use after free.
Every other path uses `with-operands` or `fence`.

**Fix.** `(fence x)` after the call, and bind the new array, then fence it,
around `retain`.

## 11. x86 portability: integer traps and casts (LOW, confirmed for x86, not yet a supported host)

- `int-division` (mlx.clj:490-496) replaces only a zero divisor. For
  `MIN_VALUE` and −1, C++ `x % y` and `x / y` are undefined, and x86's
  `idiv` raises SIGFPE: a JVM crash on the Linux x86 CPU backend. The JVM
  gives `floorDiv` = MIN and `floorMod` = 0. aarch64 (the Mac, the Thor)
  does not trap.
- `-astype` float to int (mlx.clj:1244-1246) is C++ `static_cast`:
  saturating with NaN as 0 on aarch64, as Java casts, but `INT_MIN` on x86.
  `int-power` emulates Java's cast on purpose (lines 519-527); plain
  `astype` does not.

**Test.** Conformance cases with `MIN_VALUE` and −1 operands and NaN/±Inf
casts, run on an x86 Linux CPU build.

## 12. Float `mod` of an exact multiple returns −0.0 (LOW, confirmed)

MLX's float remainder adjusts only nonzero results. On the CPU it uses
`std::remainder`, whose zero takes the sign of x
(`native/build/src/mlx/mlx/backend/cpu/simd/base_simd.h:207-221`,
`accelerate_simd.h:237-246`); Metal uses `fmod`, the same way
(`backend/metal/kernels/binary_ops.h:66-72`). So `(mod -4.0 2.0)` is −0.0 on
MLX, while the JVM (dtype.clj `floor-mod`: `(Math/copySign 0.0 y)`) and
NumPy give +0.0. It shows in `(/ 1.0 (mod -4.0 2.0))` (−Inf against +Inf)
and in the JVM backend's bitwise array equality. It is not in §13's table.

**Test.** A conformance check on the sign bit of zero results of `mod`.

## 13. Errors that are not ex-info (LOW, confirmed)

- A compiled function whose result tree has a non-array leaf (nil, a
  keyword) gets `as-array` → `scalar-handle*` → `dt/host-long`
  (mlx.clj:1150, 164-175). That throws `NullPointerException` or
  `ClassCastException`, which escapes through `UPCALL_ERROR` instead of an
  ex-info naming the leaf.
- `guarded :compile` wraps only `compile-fn`'s construction (mlx.clj:1215).
  An MLX error raised while applying the compiled closure (mlx.clj:1158)
  reaches the user as a raw `MlxException`.

## 14. Docs that disagree with the code (LOW, confirmed)

- docs/array-api.md:497-498 says a `Cleaner` frees each array "on the
  Cleaner's own thread". DESIGN.md:217 says "the `Cleaner` frees on its own
  thread". The code (MlxRuntime.java:255-310), §12.16 and §13 use phantom
  references drained by the threads that make arrays.
- `gen.backend.mlx`'s namespace doc (lines 11-13, 28, 30-37):
  - lists `gc-arrays` and `gc-bytes` but not `gen.mlx.gc-new-bytes`,
    `gen.mlx.constants`, `gen.mlx.grad` or `gen.mlx.cpu-compile`;
  - says gradients use the tape, without the native option.
- §8's "`array/compile` traces f once per input structure, shapes and
  dtypes" leaves out two facts: MLX traces again on every thread (its cache
  is thread-local, finding 3), and the structure ignores map order
  (finding 1).
- Integer `matmul` goes through the default float (mlx.clj:754-761), exact
  only below 2^24 in float32. The code comment says so; §13's table of
  differences does not.

## Checked and found sound

- **Threefry on MLX** (mlx.clj:965-1043): JAX's partitionable layout
  (counters [0, i], rotations, five key injections, the float32 and float64
  mantissa constructions).
- **Linear algebra.** `slogdet` parity: MLX's pivots are 0-based LAPACK
  swaps (cpu/luf.cpp:78-81), so counting `piv != arange` is right. The
  Cholesky NaN check and the zero-pivot `solve` and triangular-solve
  stand-ins are sound.
- **Exact enumeration.** The weight `logsumexp(s) − logsumexp(r)` is
  log p(τ) − log q(τ∖σ | σ) for "forward-sample the others, then the exact
  conditional"; I derived it independently. `-update`, `-regenerate`
  (Eq. 4.1 with retained choices as σ) and `-project` are consistent with
  it.
- **The compiled-step cache key** (mcmc.clj:77-78) captures settings, model,
  args and the address/shape/dtype structure, so the selection is implied.
  A compiled trajectory that differs from the plain one (float32, or a wrong
  gradient) cannot bias HMC or MALA: the acceptance uses plain-kernel
  scores, and compiled MALA returns its own consistent log q.
- **Upcalls.** Scratch nesting uses a child scratch, closure payloads are
  released through the dtor, `UPCALL_ERROR` propagates errors, and
  `to-host` copies views with `contiguous` before reading.
- **Static initialization.** `MlxRuntime`'s static init calls
  `mlx_device_info_get` (line 337) before installing the error handler (line
  476). mlx-c's default handler calls `exit(-1)` (mlx-c error.cpp), but the
  no-GPU `device_info` returns an empty map rather than throwing, so this is
  fragile, not broken.
- **The new CPU-compile probe** (mlx.clj:1167-1204) is thread-safe and
  remembers its result; while compile is unavailable it still has
  finding 1's ordering bug.

## Response (2026-10-19)

Fixed, each with a test that fails without the fix:
- **1, compile and map key order:** arguments follow the cached trace's own
  skeleton (`leaves-in` in `gen.array`); `compiled-functions` checks a
  reordered map.

  taking a fresh allocation per call; `large-argument-blocks-reuse-scratch`.
- **8, native linear-algebra gradients:** MLX's VJP callbacks run with the
  backend as gen.array's default; `native-linalg-gradients-need-no-default-backend`.

Documented: 12 (`(mod -4.0 2.0)` and integer `matmul` in the §13 table)
and 14 (the phantom references, the namespace doc's settings, compile's
per-thread tracing).

Tracked: 3 genclj-hfwo, 4 genclj-i8ui, 5 genclj-wx5h, 6 genclj-nezf,
7 genclj-xwfs, 9 genclj-l7xf, 10 genclj-2t5f, 11 on genclj-kw88 (x86),
